# FraudGuard

FraudGuard is a Python-based fraud and anomaly detection microservice for an e-commerce system.

The planned architecture is polyglot:

- **Go** handles the fast e-commerce request path and payment integration.
- **FraudGuard (Python)** stores transaction history, analyzes behavior, and calculates risk.
- **FastAPI** exposes FraudGuard through HTTP/REST.
- **SQLite** is used for the initial MVP database.
- **pandas + scikit-learn** will be introduced later for statistical analysis and machine-learning anomaly detection.

## Architecture

```text
Customer
   |
   v
Go E-commerce Service
   |
   | transaction event / risk request
   v
FraudGuard (Python/FastAPI)
   |
   +--> SQLite transaction history
   |
   +--> Rules Engine
   |
   +--> Risk Score
   |
   +--> ALLOW / REVIEW / REJECT
   |
   v
Go continues or blocks the order
```

# Build Progress

## Step 1 — Project foundation ✅

Created the initial Python/FastAPI project structure.

Technologies introduced:

- Python
- FastAPI
- Pydantic
- SQLite

Initial endpoints:

- `GET /` — confirms the service is running.
- `GET /health` — health check.
- `POST /transactions` — transaction ingestion endpoint.

## Step 2 — Transaction schema ✅

Every incoming transaction currently requires:

| Field | Purpose |
|---|---|
| `transaction_id` | Unique ID generated by the Go service |
| `user_id` | Identifies the customer |
| `amount` | Transaction amount; must be greater than zero |
| `timestamp` | When the transaction happened |
| `location` | Transaction/customer location signal |
| `device_id` | Device used for the transaction |

FraudGuard does **not** accept a client-supplied risk score. Risk is calculated by FraudGuard after analysis.

## Step 3 — SQLite database ✅

Created a `transactions` table containing the incoming transaction data and the eventual fraud decision.

Stored result fields include:

- `risk_score`
- `risk_level`
- `decision`
- `reasons`

`transaction_id` is the database primary key, which prevents two records from having the same transaction ID.

## Step 4 — Duplicate transaction protection ✅

FraudGuard checks whether a transaction ID already exists.

### Exact duplicate

If the transaction ID exists and all immutable transaction data matches, FraudGuard returns the previously stored result instead of creating another transaction.

The response marks this with:

```json
"duplicate": true
```

### Conflicting transaction

If the same transaction ID is submitted with different transaction data, FraudGuard returns:

```text
409 Conflict
```

This prevents an existing transaction from being silently overwritten.

## Step 5 — Initial risk engine ✅

Created `app/services/risk_engine.py`.

The risk engine currently contains the first MVP fraud rule:

### Time-of-day rule

Transactions occurring between midnight and 5:00 AM receive a small risk increase.

Current MVP behavior:

- Normal time → `0` additional points.
- 00:00–04:59 → `+10` points.

This is an initial demonstration rule, **not a production fraud threshold**. It will be tuned as the system gains real historical data.

## Step 6 — Apply risk scoring to transactions ✅

`POST /transactions` now sends the transaction timestamp to the risk engine before storing the transaction result.

The current flow is:

```text
POST /transactions
       |
       v
Validate transaction
       |
       v
Check transaction_id
       |
   +---+---+
   |       |
Exists    New
   |       |
   v       v
Compare   Risk engine
 data       |
   |        v
   |    Store result
   |        |
   +------> v
        Return response
```

## Current risk decisions

FraudGuard currently uses these score bands:

| Score | Risk Level | Decision |
|---:|---|---|
| `0–29` | LOW | ALLOW |
| `30–69` | MEDIUM | REVIEW |
| `70–100` | HIGH | REJECT |

These bands are MVP design values and are not intended to represent real-world fraud thresholds.

## Step 8 — Velocity detection ⏳

Measure how many transactions a user makes within a short time window.

Example:

```text
6 transactions
within 10 minutes
       |

Unusual velocity
       |
```

## Step 9 — Cold-start detection ⏳

Handle users with little or no transaction history differently from established users.

This prevents the system from pretending it knows a user's normal behavior when it has insufficient data.

## Step 10 — Behavioral consistency ⏳

Use signals such as:

- New device
- New location
- Unusual location
- Unusual transaction time

These signals will eventually work together rather than being treated as isolated checks.

## Step 11 — Risk scoring engine ⏳

Conceptually:

```text
Amount deviation   +30

New location        +15
Unusual time        +10
                    ---
                     95
                    HIGH
                    REJECT
```

The exact weights will be tested and tuned during development.

# MVP Goal

The first complete MVP should be able to:

1. Receive a transaction from Go.
2. Validate the transaction.
3. Store it in SQLite.
4. Detect duplicate/conflicting transaction IDs.
5. Analyze transaction behavior using multiple rules.
6. Produce an explainable risk score.
7. Return `ALLOW`, `REVIEW`, or `REJECT`.
8. Allow Go to use that decision before completing an order.

# Development Philosophy

FraudGuard is being built incrementally.

The project intentionally starts with a simple rules engine before introducing machine learning. This makes the system easier to understand, test, debug, and explain while creating the historical data needed for future anomaly detection.
